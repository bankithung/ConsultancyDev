# MCP Server for ConsultancyDev — Design Spec

Date: 2026-09-02
Status: Approved (design); implementation plan follows
Scope: backend (Django + DRF), new `backend/mcp_server/` package, small frontend addition

## 1. Goal

Give any MCP-capable AI platform (Claude Desktop, Claude Code, Claude.ai and ChatGPT
remote connectors, Cursor, VS Code Copilot, Windsurf, Gemini CLI, Codex CLI, custom
agents) complete, always-current knowledge of the ConsultancyDev CRM and the ability
to perform every operation a human user can perform through the web app, while
never exceeding that user's role, tenant and ownership scope.

## 2. Non-goals

- No direct ORM access from the MCP process. Every operation goes through `/api/`.
- No new business logic in the MCP layer. Composite tools orchestrate existing
  endpoints exactly as the frontend does.
- No OAuth authorization server in this iteration. Hosted mode uses bearer API keys.
- No changes to existing permission rules. Known authorization gaps found during
  exploration are documented in the knowledge layer, not fixed here.

## 3. Architecture

```
AI client (any platform)
   |  MCP over stdio   -- or --   MCP over Streamable HTTP (/mcp/)
   v
backend/mcp_server/   (Python, FastMCP from the official `mcp` SDK, httpx)
   |  HTTPS, Authorization: Bearer <api key>  (or JWT from username/password fallback)
   v
Django REST API  /api/   (unchanged permission, scoping, approval, audit rules)
```

- Package `backend/mcp_server/` lives in the backend tree and shares its virtualenv
  but does not import Django at runtime.
- Entry point: `python -m mcp_server` (stdio, default) and
  `python -m mcp_server --transport streamable-http --host 127.0.0.1 --port 8765`.
- Hosted mode is a separate process behind nginx at `location /mcp/`, with its own
  systemd unit. Health at `/mcp/health` (plain HTTP GET, unauthenticated).

### 3.1 Package layout

```
backend/mcp_server/
  __init__.py
  __main__.py          CLI: transport, host, port, base URL, read-only flag
  config.py            env parsing (CONSULTANCY_API_URL, CONSULTANCY_API_KEY,
                       CONSULTANCY_USERNAME/PASSWORD, CONSULTANCY_MCP_READ_ONLY,
                       CONSULTANCY_MCP_MAX_DOWNLOAD_BYTES)
  auth.py              credential resolution per request (stdio: env; http: header)
  client.py            ApiClient: transport-agnostic HTTP layer, pagination,
                       error translation, retry on 429, JWT refresh for fallback auth
  catalog.py           loads catalog.json, exposes typed views over it
  catalog.json         GENERATED by `manage.py export_mcp_catalog`
  server.py            builds the FastMCP instance; registers tools/resources/prompts
  tools/
    generated.py       list/get/create/update/delete + custom actions from catalog
    workflows.py       composite tools (student_360, convert_enquiry..., etc.)
    analytics.py       six analytics tools + health
    documents.py       upload/download
    auth_tools.py      whoami, my_capabilities, explain_permission
  resources.py         consultancy:// resources
  prompts.py           prompt templates
  knowledge/           curated markdown, exposed as resources

    documents.md, transfers.md, approvals.md, follow-ups-and-appointments.md,
```

## 4. Knowledge layer

### 4.1 Generated catalog (`export_mcp_catalog` management command)

Introspects the running Django project and writes `mcp_server/catalog.json`:

- `resources[]`: for every router prefix: name, url prefix, model, entity_type,
  allowed HTTP verbs, permission classes and the capability each maps to
  (read vs write), serializer fields (name, type, required, read_only, write_only,
  choices, max_length, related model, help), `SCOPE_READ_ONLY` fields, filterset
  params with lookup type (multi-value, id list, range, boolean, JSON-contains),
  search fields, ordering fields, pagination (envelope or bare array), custom
  actions (name, method, detail/list, path, documented body/response shape from a
  static overlay table keyed by view + action).
- `standalone_endpoints[]`: auth, role-permissions, analytics, health.
- `enums`: every TextChoices and `*_CHOICES` tuple (Role, Capability, statuses,
  stages, types, categories, outcomes, likelihoods).
- `roles`: ROLE_RANK, DEFAULTS, PROTECTED floors with reasons, ADMIN_ESSENTIALS.
- `approvals`: ENTITY_CHOICES and MUTABLE_FIELDS allowlist.
- `transfers`: TRANSFERABLE set and the requires_acceptance rule.
- `conventions`: pagination envelope, error envelope, multi-value query params,
  trailing slashes, throttle scopes and rates, cache header, upload limits and
  allowed extensions.
- `encrypted_fields`: fields that cannot be filtered, searched or sorted.
- `generated_at`, `schema_version`.

A Django test regenerates the catalog in memory and asserts equality with the
checked-in file (ignoring `generated_at`), failing with instructions to rerun the
command.

### 4.2 Curated knowledge (`mcp_server/knowledge/*.md`)

Hand-written from the exploration reports. Each file is a resource
`consultancy://knowledge/<topic>`. Content includes: the pipeline and what each
create does implicitly (registration creates a Payment; enrollment builds
installments; conversion is a client-side flow with the `enquiry` FK), role
visibility and the owner-vs-created_by rule, transfers (immediate for managers,
acceptance for employees), approvals (who can delete directly, allowlisted update
fields, the dead `appointment` entity type), physical vs digital documents,
encrypted fields, analytics caching and bare-array endpoints, multipart uploads,
multi-value filters, throttling, and every gap listed in the backend exploration
report section 8.

## 5. Tools

Naming: snake_case, `<verb>_<resource>` with singular resource names for item
tools and plural for lists (`list_enquiries`, `get_enquiry`, `create_enquiry`,
`update_enquiry`, `delete_enquiry`). Descriptions are generated from the catalog
and include the capability required, the fields with choices, and any implicit
side effects.

### 5.1 Generated per resource (from catalog)

| Tool | Notes |
|---|---|
| `list_<plural>` | params: every filterset param, `search`, `ordering`, `page`, `page_size` (max 200), `all_pages` (walks up to 20 pages). Returns the envelope or bare array exactly as the API does. |
| `get_<singular>` | by id |
| `create_<singular>` | body validated against the catalog: unknown fields rejected client-side with the list of valid fields; read-only fields stripped with a note |
| `update_<singular>` | PATCH; same validation |
| `delete_<singular>` | requires `confirm: true`; on a 403 "cannot delete records directly" the error text tells the client to call `create_approval_request` |

Resources without a verb in the API (read-only viewsets, append-only comments) only
get the tools the API supports; the catalog's `allowed_methods` decides.

### 5.2 Custom actions (one tool each)

`get_me`, `change_password`, `set_user_active`, `list_counselors`,
`get_my_subscription`, `payment_stats`, `download_document`,
`documents_expiring_soon`, `reorder_tasks`, `appointments_calendar`,
`return_student_documents`, `mark_notification_read`, `mark_all_notifications_read`,
`unread_notification_count`, `accept_transfer`, `reject_transfer`,
`transfer_inbox`, `transfer_outbox`, `approve_signup_request`,
`reject_signup_request`, `approval_pending_count`, `my_approval_requests`,
`approve_approval_request`, `reject_approval_request`, `get_role_permissions`,
`update_role_permissions`, `reset_role_permissions`, `my_capabilities`,
`analytics_overview`, `analytics_funnel`, `analytics_revenue`,
`analytics_branches`, `analytics_visa_pipeline`, `analytics_sources`, `health`.

### 5.3 Documents

- `upload_document(file_base64 | file_path, file_name, type, registration | enquiry,
  expiry_date, status)`: multipart POST; `file_path` allowed only in stdio mode.
- `download_document(id, save_to?)`: streams to `save_to` when given (stdio only),
  otherwise returns base64 up to `CONSULTANCY_MCP_MAX_DOWNLOAD_BYTES` (default 5 MB)
  and metadata only above that.

### 5.4 Composite workflow tools

| Tool | Behaviour |
|---|---|
| `whoami` | `users/me/` + `role-permissions/mine/` + branch scope summary |
| `student_360(registration_id / enquiry_id / enrollment_id)` | resolves the student and gathers enquiry, follow-ups with comments, registration, remarks, enrollments, installments, payments, refunds, documents, physical documents, visa records, appointments (by name), transfers and pending approvals touching the record |
| `convert_enquiry_to_registration(enquiry_id, overrides)` | GET enquiry, map fields the same way the frontend prefill does, POST registration with `enquiry` set, optionally PATCH enquiry status to Converted |
| `enroll_student(registration_id, program fields, installments_count, installment_amount)` | POST enrollment; returns enrollment with generated installments |
| `record_payment(...)` | POST payment with method metadata validation per method (cheque, UPI, card) |
| `search_everything(query)` | search across enquiries, registrations, enrollments, payments, documents, visa, follow-ups, tasks, users; grouped results |
| `daily_briefing(date?)` | follow-ups due, appointments today, overdue and due-soon installments, expiring documents (30 days), pending approvals, transfer inbox, unread notifications, overview analytics |
| `explain_permission(action, resource, role?)` | answers from the catalog roles, floors and the target's permission classes |

### 5.5 Annotations and read-only mode

Every tool carries `ToolAnnotations`: `readOnlyHint` for reads,
`destructiveHint=True` for delete, reject, revoke, reset and deactivation,
`idempotentHint` where true. With `CONSULTANCY_MCP_READ_ONLY=1`, write tools are
not registered at all.

## 6. Resources and prompts

Resources (`consultancy://`): `catalog` (full JSON), `schema/{resource}`,
`enums`, `roles`, `api-reference` (markdown rendered from the catalog),
`knowledge/{topic}` (one per markdown file, plus an index), `me` (live).

Prompts: `daily_briefing`, `onboard_student` (enquiry to registration to documents
to enrollment checklist), `follow_up_digest`, `pipeline_review`,
`permissions_audit`, `troubleshoot_error` (takes an error payload and explains it
using conventions and gotchas).

## 7. Authentication

### 7.1 Backend: personal API keys

- Model `ApiKey` (in `core/models.py`): `user` FK CASCADE related_name `api_keys`,
  `name` (80), `prefix` (12, indexed; the first 12 characters of the key, for
  display and lookup), `key_hash` (64, sha256, unique), `created_at`,
  `last_used_at` null, `expires_at` null, `revoked_at` null.
  Key format: `cdk_` followed by 40 url-safe random characters.
- `ApiKeyAuthentication` (DRF `BaseAuthentication`) in `core/authentication.py`:
  reads `Authorization: Bearer cdk_...` (also `X-API-Key`), hashes, looks up an
  unrevoked, unexpired key, checks `user.is_active` and `is_active_employee`,
  updates `last_used_at` at most once per minute, returns `(user, key)`. Tokens
  not starting with `cdk_` are ignored so JWT auth continues to handle them.
  Added to `DEFAULT_AUTHENTICATION_CLASSES` before JWT.
- Endpoints (`ApiKeyViewSet`, `/api/api-keys/`): `GET` lists own keys (never the
  hash), `POST {name, expires_at?}` returns the plaintext once,
  `POST {id}/revoke/`. A user manages only their own keys; a company admin may list
  and revoke keys of users in their company via `?user=<id>`. Logged to
  `core.security`.
- Revoking, deactivating the user, or `revoke_all_tokens` (extended to also revoke
  keys) takes effect immediately.

### 7.2 Frontend

The Profile page gets an "AI access keys" card: list (name, prefix, created,
last used, expiry, status), create (name + optional expiry; shows the key once
with a copy button and the MCP config snippet), revoke with confirmation.
`lib/apiClient.ts` gains `apiKeys.list`, `apiKeys.create`, `apiKeys.revoke`.

### 7.3 MCP server credential resolution

- stdio: `CONSULTANCY_API_KEY`; else `CONSULTANCY_USERNAME` + `CONSULTANCY_PASSWORD`
  (login, keep the refresh token, refresh once on 401).
- Streamable HTTP: the incoming request's `Authorization` header is forwarded
  per request; there is no server-wide credential. Requests without a bearer get
  401 from the MCP layer before any tool runs.

## 8. Error handling

- API errors become tool errors with message `"<status> <error>"` plus a `fields`
  breakdown and a `hint` from the knowledge layer (403 on delete: approval route;
  400 with both `enquiry` and `registration` set: one-student rule; 409: reference
  collision or duplicate; 429: throttle scope).
- Network errors and timeouts: one retry for idempotent GETs; then a clear error
  naming the base URL.
- Client-side validation errors list valid field names and choices from the catalog.
- All logging goes to stderr (stdio) or the process log (http); never to stdout in
  stdio mode, which would corrupt the protocol stream.

## 9. Testing

- `core/test_api_keys.py`: authentication class, endpoints, revocation, expiry,
  inactive user, company-admin listing, JWT unaffected.
- `core/test_mcp_catalog.py`: catalog freshness; every router prefix appears; every
  custom action appears; every enum appears.
- `mcp_server/tests/` (discovered by `python manage.py test mcp_server`; the
  package has an `apps.py`-free tests module using `django.test.TestCase`):
  - `ApiClient` gets an injectable `transport`; tests supply a Django
    `APIClient`-backed transport so tools hit the real viewsets.
  - Per-role smoke: for each of the five roles, list tools resolve, reads succeed
    or 403 as the authorization matrix expects, writes respect scope.
  - Composite tools: `student_360`, `convert_enquiry_to_registration`,
    `enroll_student`, `daily_briefing`, `search_everything`.
  - Document upload and download round trip.
  - Read-only mode registers no write tools.
  - stdio smoke: spawn `python -m mcp_server` with a fake key against a dummy base
    URL and assert `tools/list` succeeds and includes expected names.

## 10. Deployment and docs

- `requirements.txt`: add `mcp` and `httpx`, pinned.
- `deploy/consultancy-mcp.service`, an nginx `location /mcp/` snippet, and the
  `.env` variables documented.
- `docs/mcp/README.md` (what it is, how to get a key), `docs/mcp/clients.md`
  (config snippets for every platform), `docs/mcp/tools.md` (generated table of
  tools from the catalog), `docs/mcp/security.md`.
- Repo-root `.mcp.json` pointing at `python -m mcp_server` for Claude Code.

## 11. Open risks accepted

- Hosted mode relies on bearer keys; platforms that only support OAuth (some
  ChatGPT connector modes) need a future OAuth provider.
- Composite tools duplicate the frontend prefill logic for conversion; the mapping
  table is kept in one place (`workflows.py`) and covered by a test.
- Throttle limits (120/min burst) apply to MCP traffic like any client;
  `all_pages` walks are capped at 20 pages.
